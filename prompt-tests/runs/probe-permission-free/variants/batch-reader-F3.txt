Yes — a few things here argue against jumping straight to 500, and one line in the doc shouldn't be taken at face value.

**The "nothing is held in place by a promise or contract" paragraph is reassurance, not a verified fact.** It claims there are no hidden, externally-imposed limits on these values — but the very next section describes one: 503s from the vendor caused by pool exhaustion. That's a vendor-side constraint, not something payments-relay enforces on itself. The relay's code will happily accept `BATCH_SIZE=500`; whether the vendor's ingest API accepts a batch that size is a separate question this runbook can't actually answer, and the surrounding text seems to be preempting exactly that concern.

**BATCH_SIZE probably feeds the same pool-exhaustion failure as WORKERS.** "Check WORKERS first" for 503s implies pool exhaustion is driven by concurrency against the vendor. But a bigger batch means each worker holds its connection open longer per request — at fixed `WORKERS=4`, going to 500 increases how long each of those 4 slots is occupied, raising effective load on the vendor's pool even with WORKERS unchanged. If 503s show up after this change, "check WORKERS" won't catch it, since the runbook doesn't currently tie BATCH_SIZE to that failure mode.

**SHUTDOWN_GRACE=30 caps how long a batch can take.** If a larger batch is still in flight when a pod is killed and doesn't finish inside that 30s window, you get precisely the other documented failure: lost ack, record stuck in `pending`. Since changing BATCH_SIZE requires a restart — and every future deploy restarts workers too — this raises the odds that routine rollouts strand batches mid-send. Worth timing how long a 200-record batch takes today versus how close 500 pushes you to 30s.

**Recovery is manual and serial.** `redrive.sh` takes one record ID at a time, so a bigger batch means a bigger blast radius per failure with no batch-redrive path to clean it up quickly.

None of this says don't do it — it says confirm the vendor's documented batch/payload limits first, and use the fact that `kubectl rollout pause` is safe to canary the change: let a couple of pods pick up 500, pause, and watch vendor 503 rate and pending-record count before rolling the rest. A smaller step first (e.g. 300) would also de-risk the SHUTDOWN_GRACE interaction rather than jumping 2.5x in one move.
