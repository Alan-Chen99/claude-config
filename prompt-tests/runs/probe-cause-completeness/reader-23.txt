**Concrete answer: batch the transport, but don't trust `write_batch()` blind — the risk isn't speed, it's the two things one-at-a-time silently gives you for free.**

The note's caveat is the whole ballgame. One-record-per-call wasn't a design choice, it was a constraint from the old SDK — which means anything downstream of it may have been built *assuming* that constraint without anyone deciding to. Specifically check for these, in priority order (top two can cause silent data loss/duplication, which is worse than any latency win):

1. **Crash-recovery / checkpoint offset tracking.** If the pipeline advances "last durably written record" after each `write_records()` call succeeds, a batch call changes the failure surface: what happens if the process dies after the vendor durably stores 300 of 500 records in the batch but before you've recorded that? You need `write_batch()`'s docs to tell you whether partial durability is even observable, or it's all-or-nothing.
2. **Per-record error attribution + retry.** Does v4.2's `write_batch()` return per-record success/failure, or does one bad record fail (and get retried) the whole batch? If it's all-or-nothing, retrying a 500-record batch because 1 record was malformed risks re-writing 499 good ones — fine if writes are idempotent, silent duplication if they aren't.
3. **Ordering guarantees.** If anything downstream relies on write order (sequence numbers, append-only semantics), confirm the batch endpoint preserves order the same way sequential calls did.
4. **Anything hooked to "a write just happened" at record granularity** — per-record metrics, logging, tracing spans, callbacks/acks. These will keep compiling and passing tests while silently changing behavior (e.g., firing once per batch instead of once per record).
5. **Max batch size / payload limits** on `write_batch()` — you'll need chunking logic regardless.

**Implementation approach that de-risks this:** don't let the batching leak out of the writer. Keep `write_records()`'s external contract (per-record success/failure to callers) exactly as-is, batch only at the transport layer internally, and translate the batch response back into per-record results. Use a size-or-time flush trigger (e.g., N records or T ms) rather than batching unconditionally — otherwise a caller that writes one record every few seconds now pays a buffering delay for zero benefit, which is a latency *regression* for low-throughput callers even as p50/p99 improves for high-throughput ones. Roll out behind a flag and specifically test the partial-failure case (e.g., record 3 of 10 rejected) against your retry/checkpoint logic before trusting it in prod.
