Nothing in this config is safe to turn up — you're already at the vendor's ceiling, not below it.

- **`WORKERS=4` is not a tuning knob, it's a ceiling.** The vendor's pool is 5 per tenant, the admin console permanently holds 1, leaving exactly 4 for us. Raising it doesn't add throughput — it exceeds their pool and comes back as more `pool exhausted` 503s, which is indistinguishable from what you're seeing now.
- **`BATCH_SIZE=200` is already the vendor's documented max.** No headroom there either.
- Nothing else touches throughput: `RETRY_BACKOFF` is retry timing, `STRICT_ORDERING` is already `0` (the more-concurrent setting), `LOG_LEVEL` and `SHUTDOWN_GRACE` are unrelated.

Given the runbook says 503s are "nearly always pool exhaustion" and to check `WORKERS` first: your concrete first step is to check what `WORKERS` is actually deployed as right now, not raise it. If it's already at 4 and you're still getting pool-exhausted 503s under load, something else is competing for that pool (the admin console, or another instance of this relay you didn't expect), not a value you can fix by turning a number up.

If 4 genuinely isn't enough, the only real lever is outside this repo: get the vendor to raise the per-tenant pool above 5. Freeing the admin console's held slot might buy one more worker, but the runbook doesn't document that as a safe/supported move, so confirm with whoever owns that console before touching it.

Separately: the backlog itself isn't an emergency per the runbook — pending records are safe, and `./redrive.sh <record-id>` recovers lost acknowledgements one at a time. That's a correctness tool, not a throughput fix, so don't reach for it to try to push the queue faster.
