Short version: your runbook's entry for this symptom points at the wrong things, and the fix is a deploy rollback or roll-forward — but check one thing before you roll back.

## The runbook doesn't cover this crash

"The worker will not start" names two causes: a missing env var named in the first crash line, and an unrun migration showing as a column error. Yours is neither. `ImportError: cannot import name 'RecordBatch' from 'relay.vendor'` is a code/build problem. Don't spend time on `WORKERS` or `./migrate.sh` as the fix.

## 1. Pause the rollout

`kubectl rollout pause`. The runbook says paused is a normal state and nothing times out on it, and `./deploy.sh` rolls one pod at a time — so if it's still walking through pods, pausing keeps whatever old-code pods are still serving.

## 2. Get the full traceback, not the first line

`cannot import name X from Y` means `relay.vendor` imported fine but has no `RecordBatch`. Python appends a hint that separates the cases:

- `(most likely due to a circular import)` — two modules import each other and `relay.vendor` was half-initialized at read time.
- `(unknown location)` — shadowing or a namespace-package problem.
- no suffix — the symbol genuinely isn't there. Most likely new code shipped against a `relay.vendor` it didn't get.

On a crash-looping pod, or against the built image:

```
python -c "import relay.vendor as v; print(v.__file__); print([n for n in dir(v) if 'Record' in n])"
```

That gives you the file actually being imported and what it exports — if `RecordBatch` was renamed or moved out, you'll see its neighbour. Then diff the deploy range for `relay/vendor` and for whatever imports it. One gotcha from your own runbook: don't locate the importing module by grepping the service name, since several source modules match neither `payments-relay` nor `ledger-forwarder`. Grep for `RecordBatch`.

If `relay.vendor` is a pinned dependency rather than your code, compare its installed version in the new image against the lockfile.

## 3. Before rolling back, ask whether a migration ran this morning

This isn't in the runbook, but it follows from the ordering rule there. `./migrate.sh` is manual and separate, so it's a question for whoever deployed:

- **Added a column** — rollback is clean; old code ignores it.
- **Dropped or renamed a column** — rolling the code back lands you in exactly the failure the runbook describes: pods referencing the old name, 500ing. You'd need to reverse the migration too, or fix forward instead.
- **None** — rollback is clean.

## 4. Once it's up, the `pending` backlog

Records handed to the vendor during the crash-loop may be sitting in `pending`. Per the runbook, over an hour in `pending` is a lost acknowledgement rather than a lost record, so `./redrive.sh <id>` is safe — one id at a time. **Don't loop it.** February's incident (~900 redrives in a shell loop) rate-limited the whole tenant for an hour, and the runbook says nobody worked out the real threshold, so there's no known-safe batch size to fall back on.

## 5. Two things that'll mislead you meanwhile

- Alert volume will look worse than it is: some alerts still fire as `ledger-forwarder`, and the oldest dashboards list the service twice.
- The synthetic check hits a fixed record id every minute and alerts on its own when the vendor is down, even with nothing flowing. Check the vendor status page before drawing conclusions from it or paging anyone.

Not worth trying: `LOG_LEVEL=debug`. The crash is at import time, before there's anything to log.

If this is still unresolved by Saturday 04:00, reconciliation opens one ticket per discrepancy into the **billing** queue, not yours, triaged Monday — so unsent records become their paperwork rather than an alert you'll see.
