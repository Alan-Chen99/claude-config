Don't touch WORKERS or BATCH_SIZE — both are already hard ceilings, not tuning knobs, so neither can absorb the extra volume:

- **BATCH_SIZE=200** is already the vendor's documented max.
- **WORKERS=4** is set by the vendor's pool (5/tenant, minus 1 permanently held by the admin console). Raising it doesn't buy throughput — it just trades a controlled ceiling for `pool exhausted` 503s.
- **Horizontal scaling has the same problem.** The pool is per-tenant, not per-process. Two replicas at WORKERS=4 against the same tenant credential is 8 workers competing for 5 slots — same failure mode as raising WORKERS, just spread across pods. Worth checking your rollout strategy for this too, in case old and new pods ever run concurrently during a deploy.

So the real fix is outside this config file. Concrete steps:

1. **Measure current headroom before assuming there's a problem.** The runbook doesn't say how close to the 4-worker ceiling today's traffic runs. Compare current throughput to the theoretical max (4 workers × 200 batch ÷ average batch round-trip time). That tells you whether doubling actually breaks anything, or whether there's slack no one's measured.
2. **If headroom is insufficient, go to the vendor now.** The only way to raise the real ceiling is more pool — a bigger per-tenant allocation, or a second tenant credential to run a second worker group against. This has vendor lead time, so start it this month, not when you're already seeing 503s next quarter.
3. **Only raise WORKERS after that lands**, to match the new ceiling minus whatever the admin console still needs. Not before, and not as a guess.

Two no-regret changes that don't need the vendor:

- **Measure RETRY_BACKOFF before tuning it.** It's never been measured, and retries burn worker-slots from the same fixed pool of 4. At 2x volume, a constant retry rate is 2x the absolute retry load competing for those slots — knowing the real cost could recover throughput you're already leaving on the table.
- **Check batch fill rate.** If batches are flushing before hitting 200 (e.g., on a timer rather than a full batch), you're underusing the ceiling you already have. Free throughput, no vendor conversation required.

Leave alone:

- **STRICT_ORDERING** — unrelated to throughput, nothing depends on it today, no reason to touch it as part of this.
- **SHUTDOWN_GRACE** — in-flight work is bounded by WORKERS × BATCH_SIZE, both fixed ceilings. It doesn't grow with overall volume, so this doesn't need to move on volume grounds alone.
- **LOG_LEVEL** — specifically, don't flip to debug while chasing ramp-up issues next quarter. Debug is one line per record, and the log pipeline drops above ~2,000 lines/s — that's exactly the regime higher volume pushes you toward, so debug logging could silently drop the evidence you turned it on to capture.
