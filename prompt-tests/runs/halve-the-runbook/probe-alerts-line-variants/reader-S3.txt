## Order of operations

Your migration **drops** a column, so it runs *after* the rollout — not before.

**Before you start:** confirm bastion access is live (#platform-access, granted 8h, no auto-renew). If your current grant is near expiry, re-request now rather than mid-roll.

1. **`./deploy.sh <env>`** — builds, pushes, rolls one pod at a time. The runbook never spells the production env string; check the script.
2. **`kubectl rollout status deploy/relay`** — watch it. ~4 minutes in production. If something looks wrong, `kubectl rollout pause` is safe; a paused roll is a normal state and nothing times out on it.
3. **Wait for the roll to actually finish** — every pod on the new image. This is the load-bearing wait. Old pods still reference `legacy_id`, and dropping it early 500s them for the whole four minutes.
4. **`./migrate.sh`** — drops `legacy_id`.

One trap in step 2/3: if the new code crash-loops with a column error, the runbook's troubleshooting points at "a migration that hasn't been run." That diagnosis is inverted here. A `legacy_id` column error means the new image still references the column you're dropping — running `./migrate.sh` early makes it worse, not better. That's a code fix, not an ordering fix.

## Worker count: leave it at 4

4 isn't a tuning knob, it's the ceiling. The vendor allows five concurrent connections per tenant and the admin console holds one open permanently. Go above and you get `pool exhausted` vendor-side, which reaches you as an undifferentiated 503 — so at 2am you'd be debugging a 503 you manufactured, and the runbook's own 503 entry would send you straight back to `WORKERS`.

Scaling replicas instead of workers-per-pod doesn't escape it — the limit is per *tenant*, so more pods just multiply connections against the same five. And there's no second tenant to spread across; finance turned that down in March.

(Also: config is read once at boot with no reload mechanism, so any `WORKERS` change costs a restart regardless.)

## About the backlog

The runbook offers no lever for draining faster. `WORKERS` is at its ceiling and `BATCH_SIZE=200` is already the vendor's documented maximum. Two things not to reach for while you wait:

- **Don't loop `./redrive.sh`.** It takes one id at a time by design; the February loop got the whole tenant rate-limited for an hour, and nobody has ever found the actual threshold.
- **Don't switch to debug to watch the drain.** One line per record, and the pipeline starts dropping above ~2k lines/sec — you'd lose exactly the lines you turned it on for.

If the backlog turns out to be retry churn rather than raw throughput, `RETRY_BACKOFF=2s` is the one value the runbook flags as never measured against anything. That's a lead for later, not a change to make mid-deploy.

## Not in the runbook — my read

Step 4 is your point of no easy return. Once `legacy_id` is gone, rolling the deploy back puts code that references it in front of a database that doesn't have it. Any doubt about the new image is cheapest to resolve during steps 2–3, while pause and rollback both still work.
