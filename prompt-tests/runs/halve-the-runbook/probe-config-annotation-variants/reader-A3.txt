Turning `WORKERS` up is probably the wrong move, even though that's the intuitive read of "check WORKERS first."

The runbook says 503s are "nearly always pool exhaustion" — that means the vendor's pool is *already* being overwhelmed at current concurrency. Adding more workers sends more concurrent requests into a pool that's already maxed out, which tends to produce *more* 503s and retries, not more successful throughput. That would make your backlog worse, not better. "Check WORKERS first" reads as a diagnostic instruction (look here before anything else), not a license to increase it.

The counterintuitive fix that usually applies in pool-exhaustion situations: turn `WORKERS` **down**. Fewer concurrent requests means fewer 503s, means fewer retries competing for capacity, means the queue actually drains — even though nominal concurrency dropped.

I can't give you a specific number to set it to, though. The runbook is explicit that these config values are guesses and that changing any of them means checking the vendor's docs, the code, or the log pipeline config first — none of which I have in front of me here. Before touching `WORKERS` in either direction, I'd want to:

- Get the vendor's actual documented concurrency/rate limit for the ingest API and compare it to current `WORKERS`.
- Confirm in logs that the 503s cluster with concurrency spikes (i.e., it really is pool exhaustion, not something else masquerading as it).
- Remember config is read once at boot — changing `WORKERS` means a restart, which pauses draining while the backlog is already growing, so it's not a free lever to pull mid-incident.

If you want a throughput lever that doesn't touch the suspected root cause, `BATCH_SIZE` is the other candidate — but same caveat, the runbook flags it as a guess too, and I'd want the vendor's batch-size guidance before moving it rather than picking a number.
