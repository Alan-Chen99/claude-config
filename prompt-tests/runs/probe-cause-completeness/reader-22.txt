**Answer: don't do a blind swap. The note's last sentence is the whole risk — verify it, then switch.**

The note isn't hedging for no reason — it's flagging that "one record per call" may be load-bearing for reasons that have nothing to do with the SDK lacking a batch endpoint. That constraint is now gone, but the *other* possible reasons aren't automatically gone with it. Concretely, go find out whether any of these are true before switching:

1. **Per-record error handling.** If a caller currently does try/record → catch → dead-letter/retry-that-one, check what `write_batch()` returns on partial failure. Vendor batch APIs usually either (a) fail the whole batch on one bad record, or (b) return a per-item success/failure list you have to parse. Either way your error-handling code at the call site needs to change to match — silently batching under existing per-record error handling will misattribute failures or lose records.

2. **Ordering guarantees.** Does anything downstream assume strict order of writes? Confirm `write_batch()` preserves order (or doesn't reorder on retry) — some batch endpoints parallelize internally.

3. **Retry/idempotency semantics.** With one-at-a-time, a timeout has a clear boundary: you know exactly which record may or may not have landed. With a batch, a mid-batch timeout can leave you unsure which subset landed, which breaks naive retry-the-whole-thing logic unless the vendor's batch write is atomic or idempotent per item. Check the v4.2 docs specifically for this.

4. **Side effects per record.** Grep for anything sitting next to each `write_records()` call — checkpoint/offset advancement, per-record metrics or counters, rate-limit pacing, audit logging, a callback/webhook fired per write. Any of these implicitly assumed "one call = one record" and will need to be pulled out of the write loop and driven off the batch response instead.

5. **Payload/size limits.** Batch endpoints almost always cap batch size or payload bytes. You'll need chunking logic, and you need to know what happens when a chunk exceeds the cap (reject vs. truncate vs. error).

6. **Where your latency actually goes.** Confirm the bottleneck is per-call round-trip overhead (batching fixes this) and not something like per-record serialization or disk I/O that batching won't touch — otherwise you do the migration and don't get the win you're after.
