Short version: the deploy order is code first, migration second — and don't raise the worker count. Details below.

## Order of operations

You're dropping a column, and the runbook splits on exactly that: adds go before the restart, **drops and renames go after the roll finishes**. So the migration is the last step, not the first.

1. **Confirm the pre-conditions.** It's Wednesday, so the Friday-without-billing caution doesn't apply, and you're clear of Saturday 04:00 reconciliation by a couple of days. Sept 9 isn't month-end either, which matters because reconciliation has never seen a month-end close.
2. **`./deploy.sh <env>`** — roll out the new code that no longer reads `legacy_id`.
3. **Wait for the roll to genuinely finish.** Not "the last new pod went Ready" — the old pods have to be gone too. `SHUTDOWN_GRACE=30` means each one takes up to 30 seconds finishing in-flight sends. Until they're drained, old code that still references `legacy_id` is live.
4. **`./migrate.sh`** — run it yourself, it's not part of `deploy.sh`. This is where `legacy_id` actually drops.
5. **Watch for 503s and for records aging in `pending`.**

If anything looks wrong mid-roll, `kubectl rollout pause` is safe and nothing times out on a paused roll. But note that a paused roll is by definition *not* a finished roll — do not run `./migrate.sh` while you're paused. Old pods reading a column that just vanished is the failure this ordering exists to prevent.

## Worker count: leave it at 4

This is the part where I'd push back on the plan. Don't raise it.

`WORKERS=4` looks untuned — the runbook itself says "worked before; nobody tuned it," which reads like headroom. But there's a separate fact in the config section: the vendor's pool is **5 connections per tenant, and the admin console holds 1**. That leaves 4. The current setting isn't an arbitrary default that nobody got around to raising; it already saturates the pool exactly.

Raise it to 6 or 8 and you get 503s, which the troubleshooting section identifies as nearly always pool exhaustion with "check `WORKERS` first." That makes the backlog *worse*, not better: failed sends retry on `RETRY_BACKOFF=2s`, so you'd be adding load to a queue you're trying to drain. And since env vars are read once at boot, you'd have burned a restart to get there.

## What to do about the backlog instead

Diagnose it rather than throwing workers at it:

- **Check whether the stuck records are `pending`.** Over an hour in `pending` means a lost acknowledgement, not a lost record — that's not a throughput problem, and no amount of extra workers touches it. Redrive is safe there: `./redrive.sh <id>`, one id at a time. **Never in a loop** — the February incident redrove ~900 records and rate-limited the tenant for an hour, and nobody knows the threshold.
- **Don't flip `LOG_LEVEL` to debug to investigate.** Above ~2,000 lines/sec it drops lines, which is precisely the load where you'd be looking.
- **If it really is throughput-bound**, the binding constraint is the vendor's pool size, not your config. That's a conversation with the vendor about raising the per-tenant limit, not something you can fix tonight.

One thing to keep in your back pocket: `STRICT_ORDERING=0` rests on an assumption the team has never verified — they infer in-order ingest from acknowledgements alone, and never asked the vendor. It doesn't bite you tonight since you're not changing concurrency, but it's the reason I'd be wary of "just add workers" as a future lever even if the pool were larger.
