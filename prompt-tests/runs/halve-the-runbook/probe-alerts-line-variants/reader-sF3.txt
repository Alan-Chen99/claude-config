## The likely cause is arithmetic

The vendor pool is 5 connections per tenant. The admin console holds 1. That leaves 4. `WORKERS=4`.

You are sitting exactly on the ceiling with zero headroom. Any single extra connection tips it: a second person opening the console, a retry that opens rather than reuses, a connection not yet released. That's consistent with 503s that come and go rather than pinning.

So the runbook's "check `WORKERS` first" is right, but note the direction — **there is no room to raise it, only to lower it.** Drop to 3.

This assumes one pool connection per worker. The runbook implies that link (it's why `WORKERS` is the first thing to check for pool exhaustion) but never states it. If the client multiplexes, the arithmetic changes.

The change itself is cheap to make: `WORKERS=4` is explicitly "worked before; not tuned or engineered" — nobody picked 4 for a reason, so there's no argument to have. Contrast `BATCH_SIZE=200`, which is a vendor limit and not yours to touch.

## Confirm three things first

1. **How many instances?** The runbook says "the roll" and `rollout pause`, which implies more than one. If N replicas each run `WORKERS=4`, you're at 4N against a pool of 5 — the console isn't your marginal consumer, you're structurally over, and the fix is much smaller than 3. Establish this first; it determines the answer.
2. **Is anyone on the admin console right now?** That's the 5th connection. If the 503s track console use, you've confirmed the theory *and* you have a mitigation that needs no deploy.
3. **Does the every-minute synthetic check hold a pool connection?** The runbook mentions it only to explain alerts with no traffic. If it also takes a connection, your budget was never 4.

## Shipping it

Config is read at boot, so this needs a restart — and the restart is the risky part. `SHUTDOWN_GRACE=30` means old workers hold in-flight sends for up to 30s, so during a roll old and new overlap and connection count goes *up* before it goes down. You can make the 503s worse mid-deploy.

`rollout pause` is safe — nothing times out on a paused roll — so pace it one instance at a time and let the old side drain past 30s before starting the next. No schema change, so `./migrate.sh` isn't involved. There's no staging, so this lands straight in prod; that's the other reason to go slowly.

## Four traps, all live right now

- **Don't flip `LOG_LEVEL` to debug.** Debug drops above ~2k lines/s, and a 503 storm is exactly when you're above that. You'd lose the lines you turned it on for.
- **Don't bulk-redrive the backlog.** The 503s will have left records in `pending` and the instinct is to loop `./redrive.sh`. February: ~900 records, tenant rate-limited an hour, threshold still unknown. One at a time, by design.
- **Those pending records aren't lost.** `pending` is hand-off, `sent` is their ack; over an hour means a lost acknowledgement, not a lost record. Don't let it drive the urgency.
- **Your 503 count may be wrong in both directions.** The oldest dashboards list the service twice, and older alerts fire as `ledger-forwarder`. Check you aren't double-counting, and that 503s under the old name aren't missing from what you're looking at.

## If 4→3 doesn't clear it

`RETRY_BACKOFF=2s`, never measured. If a 503 triggers a retry and the retry opens a connection, 2s feeds the exhaustion and the failure sustains itself. The runbook calls it "a fine place to start if retries need work" — retrying into an exhausted pool qualifies. But change one thing at a time, and `WORKERS` is the one with arithmetic behind it.

One non-worry: going 4→3 doesn't threaten ordering — fewer concurrent senders is strictly safer for send order. (And the belief that the vendor ingests in send order is inferred from acks alone, never asked and never documented by them, so it isn't a firm constraint to trade against either way.)
