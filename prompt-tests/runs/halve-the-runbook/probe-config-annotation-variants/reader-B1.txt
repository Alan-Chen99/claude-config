Nothing in this config is safe to turn up — and `WORKERS` in particular is already maxed, not under-utilized.

**Why `WORKERS` is a dead end:** the vendor allows 5 concurrent connections per tenant, and the admin console permanently holds 1 of those. That leaves exactly 4 — which is the current setting. `WORKERS=4` *is* the ceiling, not a starting point. Pushing it to 5 would blow through the vendor's per-tenant limit outright, which is very likely *why* you're seeing 503s under load in the first place (the runbook flags 503s as "nearly always pool exhaustion" and says to check `WORKERS` first). Raising it would add more concurrent load onto an already-saturated pool and make the backlog worse, not better.

**The other variables don't help either:**
- `BATCH_SIZE=200` is a vendor-imposed limit. Increasing it could in theory raise throughput (more records per send instead of more concurrent sends), but the runbook is explicit that you need to check their docs first — I don't have that doc in front of me, so I can't hand you a safe number.
- `RETRY_BACKOFF=2s` is freely changeable, but lowering it doesn't add capacity — it just throws retries at a vendor that's already returning 503s, sooner. That's more likely to deepen the pool exhaustion than relieve it.
- `STRICT_ORDERING`, `LOG_LEVEL`, `SHUTDOWN_GRACE` — unrelated to throughput.

**So the honest answer is: there's no config knob here that increases throughput safely.** You're pinned at the vendor's hard concurrency ceiling. Real options are outside this file:
1. Ask the vendor for a higher per-tenant concurrency limit (or whether the admin console's reserved slot can be released).
2. Confirm with the vendor's docs whether `BATCH_SIZE` can go above 200 — that raises throughput per connection instead of connection count, which is the only lever that doesn't fight the concurrency cap.
3. Apply backpressure upstream and let the queue drain at the pace the vendor allows, rather than trying to push more concurrency into it.
