## Order of operations

This is a **drop**, so the migration runs last:

1. **Confirm the new code no longer reads or writes `legacy_id`.** The drop-after-roll rule only protects you if the rolled code has already stopped touching the column.
2. **`./deploy.sh <env>`** — roll first. Nothing migrates ahead of the restart; the "before the restart" half of the rule is for column *adds*.
3. **Wait for the roll to finish.** The runbook's wording is asymmetric on purpose: adds go before *the restart*, drops go after *the roll finishes*. That means every instance on the new code, not just the first one restarted. If anything looks off, `rollout pause` is safe — nothing times out on a paused roll. This is your last abort point; step 4 isn't reversible.
4. **`./migrate.sh`** — the drop.

One wrinkle the runbook doesn't cover: it assumes the rolled code is the only thing that touches the column, and you're rolling into a backlog. If the queued records were written by the old code and anything on the drain path still reads `legacy_id` off them, the real gate for step 4 is the backlog draining, not just the roll finishing. Worth confirming before you run it.

## Worker count: leave it at 4

You can't add workers. `WORKERS=4` is a ceiling, not a knob — the vendor pool is 5 connections per tenant and the admin console holds one, which leaves exactly 4. Raising it doesn't buy throughput; it takes the console's connection and exhausts the pool. And the runbook's own 503 triage is "check `WORKERS` first," so you'd be manufacturing the failure you'd then be paged for.

## So where does the drain come from

- **Check what the backlog actually is first.** `pending` means handed off to the vendor, not unsent — `sent` only lands on their ack. Over an hour in `pending` is a lost acknowledgement, not a lost record. If your queue-depth metric counts `pending`, part of that "backup" may already be delivered, and no amount of worker capacity would move it.
- **`RETRY_BACKOFF=2s`** is the one value the runbook marks free to change — but it's never been measured, so any improvement is a guess, not a plan. Config is read at boot, so it would land on the restart you're already doing; bundling it means you can't tell the deploy's effect from the backoff's.
- **`BATCH_SIZE=200`** carries no annotation at all — the runbook doesn't say what constrains it, so it isn't a known-safe lever. Ask before turning it.
- **Don't loop `./redrive.sh`.** It's one at a time by design. The February incident was ~900 records and got the tenant rate-limited for an hour, and the threshold is still unknown — a backing-up queue is exactly the situation that makes looping it tempting.

## Also worth having in mind tonight

- There's no staging, and that's a finance decision, not a gap to route around — the drop gets no rehearsal, so step 4's first run is production.
- Older alerts fire as `ledger-forwarder`; same service.
- If traffic drops during the roll and an alert fires anyway, that's likely the synthetic check — it runs every minute against a fixed record id and alerts on vendor downtime independent of your traffic.
- Don't flip `LOG_LEVEL` to debug to watch the drain: above ~2k lines/s it drops lines, so a backlog is when it's least likely to show you what you turned it on for.
- If you end up rewriting the branch, `CONTRIBUTING.md` §4 covers force-pushing.
