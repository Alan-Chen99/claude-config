## Order of operations

Your change is a **drop**, so the migration goes last:

1. **`./deploy.sh <env>`** — ship the code that no longer reads `legacy_id`.
2. **Wait for the roll to *finish*** — not just the first restart. The runbook splits these deliberately: adds go before *the restart*, drops and renames after *the roll finishes*. Any instance still on old code is still referencing `legacy_id`, so a partial roll that looks healthy is not the signal to proceed.
3. **`./migrate.sh`** — drop the column.

Two things about that gap between 2 and 3:

- It's your last cheap rollback point. Once the column is gone, rolling back to code that reads `legacy_id` isn't an option, and there's no staging to have rehearsed it in.
- If anything looks off mid-roll, `rollout pause` is safe — nothing times out on a paused roll, so you can stop and look without a cascade.

Expect some records to land in `pending` from workers cycling through `SHUTDOWN_GRACE=30`. That's a lost acknowledgement, not a lost record, and only after an hour. `./redrive.sh <id>`, one at a time — don't loop it, even to clean up post-deploy.

## Worker count

**Leave it at 4.** This is the one thing you asked for that the runbook refuses: `WORKERS=4` is a ceiling, not a knob. The vendor pool is 5 per tenant and the admin console holds 1, so 4 is already the whole budget. Raising it doesn't add throughput — it produces 503s, which is exactly the failure the runbook tells you to diagnose by checking `WORKERS` first. You'd be manufacturing the symptom while on call for it.

So there's no concurrency lever here. On the backlog itself:

- `RETRY_BACKOFF=2s` is the one config marked free to change, but "never measured" means nobody knows it's the constraint. It only helps if the backlog is retry-driven, and shortening it pushes harder against a vendor that has rate-limited you before.
- `BATCH_SIZE=200` is the only plausible way to move more records without more connections. But the runbook annotates every setting it has knowledge about, and this one is bare — that's absence of evidence, not a green light. I wouldn't stack it onto tonight's deploy: config is read at boot, so it would ride this restart, and then a rollback is changing two variables at once with a column drop in between.

If the queue genuinely needs to drain faster than 4 workers allow, that's a conversation with whoever owns the vendor relationship about the per-tenant pool size, not a config edit tonight.
