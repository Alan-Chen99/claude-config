## Deploy order

`legacy_id` is a **drop**, so the migration runs *after* the roll — the reverse of a column add.

1. **Confirm the code you're shipping doesn't touch `legacy_id`.** It's what will be running when the drop lands, so it has to survive the column's absence.
2. **`./deploy.sh <env>`** — not `shipit`. Both work; the runbook's point is that switching is a conversation with the team, not a swap to make mid-incident.
3. **Let the roll finish completely** — not just the first restart. The runbook says "after the roll finishes," and the distinction is the whole point: a half-rolled fleet still has old instances reading `legacy_id`. Each instance drains in-flight sends up to `SHUTDOWN_GRACE=30`, and with the queue backed up, expect close to the full 30s per instance.
4. **If anything looks off mid-roll, `rollout pause`.** Nothing times out on a paused roll, so pausing costs you time and nothing else.
5. **`./migrate.sh`** — run the drop only once every instance is on new code.

No config change to bundle in, which is just as well: config is read at boot, so any change means another restart.

## Worker count: leave it at 4

You can't raise it. `WORKERS=4` isn't a tuning knob, it's arithmetic — the vendor pool is 5 per tenant and the admin console holds one, so four is what's left. Setting 5+ doesn't buy throughput, it exhausts the pool, and the failure mode is 503s — which the runbook's own triage sends you back to `WORKERS` to diagnose. You'd spend the night chasing the change you made.

The only other slot is the admin console's, and taking it leaves you without the console while on call.

## On the backlog

The runbook gives you no throughput lever:

- `WORKERS` — at ceiling, per above.
- `BATCH_SIZE=200` — a vendor limit, not ours.
- `RETRY_BACKOFF=2s` — the one value flagged as adjustable, and explicitly never measured. Worth touching only if the backlog is retry churn rather than send volume, and then it's an experiment, not a fix.

**Do not loop `./redrive.sh`.** It's the obvious reach for a backlog and it's the one thing the runbook bans outright — February, ~900 records, tenant rate-limited for an hour, threshold still unknown. The single-id form is safe, one at a time.

Also worth separating: a backing-up send queue isn't the same as stuck `pending`. `pending` past an hour is a lost acknowledgement, not a lost record.

## Two things for tonight

- If you reach for `LOG_LEVEL=debug` to investigate the backup: debug drops above ~2k lines/s, so a high-volume backlog is precisely the condition where you lose the lines you turned it on for. Plus it needs a restart to take effect.
- Alerts: `ledger-forwarder` is this service under an older name. And the synthetic check fires every minute against a fixed record id independent of real traffic — it can alert during the roll on its own, and a green one doesn't tell you real sends are working.
