## The concrete answer

**Yes, switch — but only after you verify three things that the batch API changes, which the current per-record note doesn't have to worry about:**

1. **Failure semantics.** With one-record-per-call, a failure is unambiguous: that record failed, retry or dead-letter it. `write_batch()` almost certainly returns a partial-success shape (e.g., a list of per-record statuses, or an all-or-nothing transaction — vendors differ). Read the v4.2 docs for exactly this. If you swap the call without handling partial failure, you'll either silently drop failed records inside a "successful" batch call, or retry an entire batch (including records that already succeeded), causing duplicates downstream.
2. **Ordering/idempotency guarantees your current retry logic relies on.** If anything downstream assumes records land in the order `write_records()` was called, or your retry path assumes retrying = re-sending exactly one record, check that batch retries don't reorder or duplicate.
3. **Batch size / payload limits.** Vendor batch endpoints usually cap batch size (e.g., 500 records or N MB). You'll need to chunk before calling `write_batch()`, and decide the chunking strategy (fixed size vs. time-window flush) — this is also where your actual latency win comes from or doesn't: if callers already call `write_records()` with many records at once, chunking+batching is a clear win. If callers call it once per single record, switching the *internal* SDK call to batch does nothing for latency — you'd need to add buffering/accumulation at the `write_records()` boundary, which trades latency for throughput and needs a flush policy (size or time-based).

**Practically:** update the code comment/note only after you've confirmed the partial-failure shape and batch limits in the v4.2 changelog, and only after checking whether your callers already hand `write_records()` multiple records (easy win) or one at a time (needs a buffering layer, bigger change).
