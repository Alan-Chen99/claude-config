## Order of operations

Your change is a **drop**, so the migration goes *after* the roll, not before:

1. **Set `WORKERS` now if you're changing it at all** (see below — I don't think you should). Env vars are read once at boot, so it has to be in place before the roll or you'll need a second restart.
2. **`./deploy.sh <env>`** — ships the code that no longer reads `legacy_id`.
3. **Wait for the roll to actually finish.** Not "new pods Ready" — old pods *gone*. `SHUTDOWN_GRACE=30` means a terminating worker keeps sending for up to 30s, and that's old code still touching `legacy_id`.
4. **`./migrate.sh`** — you run this yourself; `deploy.sh` doesn't.
5. Verify, then watch the queue.

If anything looks wrong mid-roll, `kubectl rollout pause` is safe and nothing times out while paused. But a paused roll means old and new pods side by side — **do not run `migrate.sh` in that state.**

## Worker count: leave it at 4

The vendor's pool is 5 connections per tenant and the admin console holds 1. That leaves 4, and you're running 4. There is no headroom.

Raising `WORKERS` to drain a backlog is the exact thing your troubleshooting section warns about: 503s are "nearly always pool exhaustion — check `WORKERS` first." You'd trade a slow queue for a failing one, tonight, on call.

The `WORKERS=4` line says "nobody tuned it," which makes 4 look arbitrary. It happens to be the ceiling anyway — but that's coincidence, not tuning, so treat 4 as a cap you can't exceed rather than a number anyone validated as optimal.

## Before you assume throughput is the problem

**Check whether the backlog is unsent or unacknowledged.** A record is `pending` on hand-off and `sent` on their ack. If your backed-up records are `pending` over an hour, those sends already happened — you're missing acknowledgements, and more workers would do nothing. Redrive is the fix there, one id at a time. Never in a loop.

Two other things that could be distorting the picture:

- **The oldest dashboards list this service twice.** If that's where the queue depth is coming from, the number may be inflated.
- **`ledger-forwarder` alerts are this service**, and a synthetic check hits a fixed record id every minute — so expect alerts during the quiet stretch of the roll that aren't real traffic.

One flag: raising workers also increases send concurrency, and `STRICT_ORDERING=0` rests on an assumption nobody has confirmed with the vendor. Another reason not to touch it tonight.
