Yes — two signals, plus one you should specifically *not* read as vendor health.

**The synthetic check.** It runs every minute against a fixed record id, independently of what we send. That's the closest thing you have to a purpose-built liveness probe: it doesn't need our traffic to be flowing, so it separates "vendor is down" from "we happen to be quiet." Caveat: it's one fixed id on one path, so a pass proves their endpoint answers, not that real records are ingesting cleanly.

**The `pending` → `sent` transition rate.** `sent` is set on *their* acknowledgement, so anything moving to `sent` right now is direct evidence they're alive and acking. Read it in aggregate, not per-record — the runbook is explicit that one record over an hour means a lost acknowledgement, not a lost record or a down vendor. The vendor-down shape is newly handed-off records staying `pending` across the board with nothing transitioning.

**Don't use 503s.** The runbook's default reading is pool exhaustion on our side, so a 503 spike is evidence about `WORKERS`, not about them.

If you're tempted to hand-roll a probe, two things to watch:

- Their pool is 5 connections per tenant, the admin console holds 1, and `WORKERS=4`. If each worker holds a connection, we're at exactly the ceiling with no headroom — an ad-hoc curl can 503 on our own exhaustion and read as an outage.
- Don't loop `./redrive.sh` to manufacture traffic for the test. That rate-limited the tenant for an hour once, which would itself look like the vendor refusing us.

Worth knowing about both live signals: the runbook flags elsewhere (the `STRICT_ORDERING` note) that we infer the vendor's behaviour from their acknowledgements alone, never asked, and they never documented it. Acks are what we have, but nobody has confirmed with them what an ack does and doesn't mean.
