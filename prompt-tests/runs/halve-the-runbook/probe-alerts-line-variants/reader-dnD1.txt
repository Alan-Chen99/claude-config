## Worker count: leave it at 4

Don't raise it. The vendor's pool is 5 connections per tenant and the admin console holds 1, leaving 4. `WORKERS=4` is already sitting on that ceiling. The runbook also says 503s are nearly always pool exhaustion and to check `WORKERS` first — so raising workers on a backed-up queue is the change most likely to turn a slow queue into a failing one.

Two caveats, both pointing the same way:

- The runbook never states that one worker holds one connection — the 4 = 5−1 match is my inference. It doesn't change the decision: more workers means more concurrent connections against a hard limit of 5, and you're at or near it either way.
- `WORKERS=4` was never tuned ("worked before; nobody tuned it"), so 4 isn't a proven optimum. It's just that there's no headroom above it to buy.

You could close the admin console to free its connection and run 5 — a 25% bump, at the cost of having no console on the night you're on call and deploying. Bad trade.

Also worth knowing: config is read at boot, so there's no "run more workers while it drains." Any `WORKERS` change is another restart on top of the deploy's roll. And more concurrency would lean harder on the assumption behind `STRICT_ORDERING=0` — that the vendor ingests in send order, which the runbook says was inferred from acks alone, never asked and never documented.

## Deploy order

You're dropping a column, so the migration goes **last**:

1. **Confirm the new code has no remaining references to `legacy_id`.** There's no staging, so this is the only place it gets caught.
2. **`./deploy.sh <env>`**
3. **Wait for the roll to fully finish** — every instance on new code, none left. Mid-roll you still have old instances reading `legacy_id`. If you need to stop and check, `rollout pause` is safe (nothing times out on a paused roll) — but don't migrate while paused, since paused means a mixed fleet.
4. **`./migrate.sh`** — the drop.

That's the runbook's rule applied literally: adds go before the restart, drops and renames after the roll finishes. `legacy_id` is a drop, so nothing runs before the deploy.

Two things I can't resolve from the runbook: it doesn't say how `./migrate.sh` selects which migration, or whether it takes an env argument the way `deploy.sh` does — check that before you're mid-deploy. And each instance's shutdown waits up to `SHUTDOWN_GRACE=30` for in-flight sends, so the roll will suppress throughput while the queue is already backed up. Expect the backlog to grow during the deploy, not shrink.

## On the backlog itself

Workers are the wrong lever, and the runbook doesn't name the right one, so start by finding out what the queue is blocked on:

- **Seeing 503s?** That's pool exhaustion — more workers makes it worse.
- **Lots of `pending`?** `pending` is hand-off, `sent` is their ack. Over an hour is a lost acknowledgement, not a lost record — those went through and aren't backlog to re-send.
- **Don't loop `./redrive.sh`** to clear it. One at a time by design; February was ~900 records and an hour of tenant rate-limiting, threshold unknown.
- **Don't reach for `LOG_LEVEL=debug`** — above ~2k lines/s it drops lines, which is exactly the regime a backed-up queue puts you in.
- `BATCH_SIZE=200` is the vendor's limit, not yours, so it isn't a knob. `RETRY_BACKOFF=2s` was never measured — if this turns out to be retry-driven, that's the one worth investigating, but measure before changing it.
