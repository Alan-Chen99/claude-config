## The runbook's answer doesn't fit this crash

"The worker will not start" gives two causes, and your first line rules out both:

- **Missing env var** — the runbook says it's *named in the first line*. Your first line names a Python symbol, not an env var.
- **Unrun migration** — shows up as a *column* error. This is an `ImportError`, raised at import time, before config parsing or any DB access.

So this is the one the runbook doesn't cover. Don't burn time on `WORKERS` or the rest of the config block.

## What the error actually means

`relay.vendor` was found and loaded, but `RecordBatch` isn't bound in it. Two families:

1. **Version skew** — this morning's code expects a `relay.vendor` containing `RecordBatch`; the copy in the deployed image doesn't have it. Vendored directory not updated with the code that uses it, dependency not re-pinned, or a stale build layer.
2. **Circular import** — something imports `relay.vendor` while it's still initializing, so the name isn't defined yet. Produces this exact message, and is a common result of a deploy that adds one new import.

## Right now

1. **Check whether old pods are still serving.** `deploy.sh` rolls one pod at a time, so you may be degraded rather than down — that changes how much time you have.
2. **`kubectl rollout pause`.** The runbook is explicit that paused is a normal state and nothing times out on it. Freezes the roll while you diagnose.

## Diagnosing (should take minutes)

- **Get the full traceback, not the first line.** The last frame before the `ImportError` names the module doing the import — that alone usually separates skew from circular.
- In the failing image: `python -c "import relay.vendor as v; print(v.__file__); print(sorted(dir(v)))"`. Imports fine standalone with no `RecordBatch` → skew. Errors only under the app's import order → circular.
- Diff the vendored code and the pin between last-good and deployed: `git diff <last-good>..<deployed> -- relay/vendor/ requirements*.txt`.

## Fixing

Rolling back is probably fastest — but note **the runbook documents no rollback**. `deploy.sh` only rolls forward, so you'll be deploying the previous version by whatever informal means exist, with no written procedure. Worth writing that section afterward.

And with **no staging**, you verify the fix on your laptop or in production; a second tenant needs finance, who turned it down in March.

## Before and after you're back up

- **Check for a pending migration before you restart.** Otherwise you may fix the import and immediately crash-loop on the column error the runbook names as the next cause.
- **Backlog:** `pending` means handed to the vendor, not lost. Redrive one id at a time — `./redrive.sh <record-id>`, **never in a loop**. About nine hundred in a shell loop rate-limited the whole tenant for an hour in February, and nobody has worked out the real threshold, so "one at a time" is a standing constraint rather than a tuned number.
- Any `ledger-forwarder` alerts firing are this same service under an old name — one incident, not two.

I can't see your repo or the full traceback, so the skew-vs-circular split is the one thing I'd resolve first; everything downstream depends on it.
