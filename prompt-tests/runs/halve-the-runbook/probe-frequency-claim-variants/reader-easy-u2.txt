Start with the first line of the crash output — the runbook says that's where the cause is named, and it discriminates between the two known causes.

**If it names an environment variable:** set it and restart. Config is read at boot with no reload, so there's no way to apply it to the running process. One trap if the missing variable is `WORKERS`: 4 is a ceiling, not a tuning knob — the vendor allows five concurrent connections per tenant and the admin console permanently holds one, so anything above 4 gets you `pool exhausted` surfacing as an undifferentiated 503. You'd fix the boot failure and buy a harder-to-diagnose one.

**If it's a column error:** that's an unrun migration. `./migrate.sh` is run by hand, separately from `./deploy.sh`, and add-a-column migrations are supposed to go *before* the restart precisely because new code writes to the column on boot and crash-loops without it — which is the symptom you have. So run it now, then restart.

**A few things worth knowing while you work:**

- If you're mid-roll, `kubectl rollout pause` is safe. Paused is a normal state and nothing times out on it, so you can stop the roll while you sort out the cause rather than racing it.
- When you go looking through logs and alerts, the service answers to more than one name: some old alerts fire as `ledger-forwarder`, several source modules match neither name, and the oldest dashboards list it twice. It's all one service — don't read a name mismatch as a second system.
- There's no staging, so you can't reproduce this off production. That's deliberate (the vendor bills per tenant and finance declined a second one in March), not a gap someone forgot to fill — ask finance before assuming you can spin one up.

One caveat on the above: the runbook says a missing env var is the cause *often*, and lists the migration case alongside it. Those are the two common causes, not a closed set. If the crash output's first line points at neither, the runbook doesn't cover what you're seeing and you're past what it can tell you.
