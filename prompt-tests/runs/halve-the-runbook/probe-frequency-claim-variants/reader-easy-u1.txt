Working from the runbook you pasted — I can't reach your cluster, so this is what it tells you to do.

**Get the crash output first.** The runbook says the cause is named in the first line of it.

```
kubectl logs <pod> --previous
```

`--previous` because a crash-looping pod's current container often hasn't logged anything yet.

Two documented causes:

**1. Missing environment variable** — named in that first line. The runbook calls this the frequent case, not the certain one. Set it and restart the pod: config is read at boot with no reload, so setting the variable without a restart changes nothing.

**2. Unrun migration** — shows up as a column error on boot. If the deploy you're rolling adds a column, `./migrate.sh` was supposed to run *before* the restart; new code writes to the column on boot and crash-loops without it. That is this symptom exactly. Run `./migrate.sh` now, and the pods that already rolled will boot once the column exists.

If you're mid-roll, `kubectl rollout pause` is safe — the runbook says paused is a normal state and nothing times out on it, so you can stop the roll while you sort the migration out.

A drop/rename migration run too early looks different: the runbook says not-yet-replaced pods 500 rather than fail to start. So a column error at boot points at the add-column case.

**If the first line is neither of those,** the runbook stops there — it names two causes and doesn't say they're the only ones. Two notes before you go hunting: turning on `LOG_LEVEL=debug` is one line per record and the pipeline drops above ~2000 lines/sec, so it can lose the lines you turned it on to see. And there's no staging, so whatever you try next is production.
