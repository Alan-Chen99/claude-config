**`WORKERS=4`** — and treat it as the maximum, not a starting point.

The reasoning the runbook gives: the vendor's connection pool is 5 per tenant, and the admin console permanently holds 1 of those. That leaves 4 for the relay. It's arithmetic against an external limit, not a performance setting someone tuned.

Two things that follow:

- **Don't raise it.** Going above 4 contends with the admin console for the last slot. The runbook notes 503s are nearly always pool exhaustion and says to check `WORKERS` first — so if you see 503s later, the check is "has someone pushed this past 4," not "should I add workers."
- **You could go lower, but there's no stated reason to.** A ceiling permits less; nothing in the runbook suggests fewer than 4 helps.

Also relevant for a deploy config: config is read at boot, so changing this needs a restart, not a reload.
