A few things in the runbook argue for caution, not just "it's a number, bump it":

1. **It's not a live tune.** `BATCH_SIZE` is read once at boot, so this isn't a quiet knob turn — it needs a restart/redeploy. If you want to stage it, `kubectl rollout pause` being called out as safe suggests that's the intended way to land it incrementally rather than all-at-once.

2. **The "check `WORKERS` first" note isn't independent of `BATCH_SIZE`.** 503s are pinned on pool exhaustion, and the pool is sized by `WORKERS=4`, unchanged. Bigger batches mean each worker holds its outbound slot to the vendor longer per cycle — same pressure on the pool as if you'd quietly reduced worker count. Pushing `BATCH_SIZE` up while leaving `WORKERS` fixed is a plausible way to start seeing exactly the 503s that section warns about, without having touched the thing it tells you to check.

3. **Read the "nothing here is a promise" line as a warning, not reassurance.** It's telling you 200 isn't policy you need permission to change — but also that if 500 is wrong, nothing in this doc will tell you in advance. You'll find out because "the system enforces it": the vendor's ingest API rejecting/erroring on an oversized batch, or a timeout, not a documented ceiling. Worth confirming the vendor's actual max batch size before assuming 500 is inside it.

4. **Blast radius on failure goes up.** The known failure mode here is a lost ack (record's fine, ack isn't), and redrive is explicitly one-id-at-a-time. A bad batch at 500 is 2.5x the manual redrive toil of one at 200, for the same failure you're already used to seeing.

None of this says don't do it — but I'd confirm the vendor's documented batch limit first, watch the 503 rate against `WORKERS` after the bump (not just throughput), and consider stepping up (e.g. 200→350) rather than jumping straight to 500, using the rollout-pause to watch each step.
