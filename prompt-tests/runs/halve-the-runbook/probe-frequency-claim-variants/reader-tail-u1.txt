## Short version

Your runbook's "worker will not start" entry doesn't cover this. It names two causes — a missing environment variable (named in the first line) and an unrun migration (showing as a column error). An `ImportError` on a Python symbol is neither, so don't spend time on env vars or `./migrate.sh`. The image itself is internally inconsistent: something in it imports `RecordBatch` from `relay.vendor`, and the `relay.vendor` in that image doesn't define it. No amount of config will fix that.

## Do this first

1. `kubectl rollout pause`. Your runbook says this is safe and that paused is a normal state nothing times out on — and since `deploy.sh` rolls one pod at a time, pausing keeps whatever old pods are still up forwarding records.
2. `kubectl get pods` to see how far the roll got. That tells you whether you're degraded or fully down, which sets how much time you have to diagnose vs. roll back.

## Then decide: roll back, or fix forward

Rollback is usually right for a hard ImportError at boot — there's nothing to debug in prod. One thing to check before you do it: **did anyone run `./migrate.sh` this morning, and what kind of migration was it?** Your runbook gives the ordering rules for deploying forward but not for going backward, and the direction matters. An add-column migration is harmless to roll back under — old code just ignores the column. A drop-or-rename that's already applied means the old code references a name that isn't there anymore and will 500, which is the same failure your runbook describes for not-yet-replaced pods, reached from the other side. If a rename or drop went in, code-only rollback isn't safe.

To actually diagnose, in the failing image:

```
python -c "import relay.vendor as v; print(v.__file__); print(sorted(dir(v)))"
```

That distinguishes the three candidates: an unexpected `__file__` means something is shadowing the module or a namespace-package layout changed; the expected path with `RecordBatch` missing means version skew between app code and the vendored tree; and if the full traceback says "most likely due to a circular import," it's an import-ordering bug in the new code, not a stale dependency. **Read the whole traceback, not just the first line** — that phrase is the cheapest signal available and it's not in what you pasted.

Then `git log --oneline <prev>..<deployed> -- relay/vendor/` plus `git grep -n RecordBatch`. If `RecordBatch` is new in application code and absent from the vendored module, the vendor bump didn't ship with the code that needs it. If `relay.vendor` is generated from the vendor's SDK, check that the image build actually re-ran that step.

## Two things not to reach for

**Don't redrive.** `./redrive.sh` is for records over an hour in `pending`, and `pending` means already handed to the vendor with the acknowledgement lost. Records that never left because the worker was down aren't in that state, so redrive is the wrong tool — and the no-loop rule is absolute regardless: ~900 redrives in a loop rate-limited the whole tenant for an hour last February, and since nobody's established the real threshold, there's no safe loop size to pick instead.

**Don't try to verify in staging.** There isn't one, and per your runbook that's a decision finance made in March, not a gap someone can fill today. Reproduce on your laptop instead: run the deployed image's entrypoint locally and you should hit the identical ImportError immediately. For this failure class that's a complete reproduction, since it happens at import time before anything touches the vendor or the ledger.
