Two answers up front: **deploy the code first, migrate second** — and **leave `WORKERS=4`**, don't raise it.

## Order of operations

1. **`./deploy.sh <env>`** — code goes out first.
2. **Wait for the roll to fully finish.** Not just the first restart — every instance on the new code.
3. **`./migrate.sh`** — drop `legacy_id` now.

The runbook splits migrations by direction: adds go *before* the restart, drops and renames *after the roll finishes*. Yours is a drop, so it's the "after" branch — and note the anchor is roll *completion*, not restart. Mid-roll you have old and new code running side by side, and the old instances still reference `legacy_id`. Drop it before the roll drains and those instances break against a column that's gone.

If anything looks wrong mid-roll, `rollout pause` is safe to reach for — nothing times out on a paused roll, so you can stop and look without a clock running against you.

## Worker count: leave it at 4

`WORKERS=4` is already the maximum, not a default someone picked conservatively. The vendor pool is 5 per tenant and the admin console holds 1 — 4 is the entire remainder. Raising it doesn't buy throughput, it oversubscribes the pool.

And it fails in exactly the shape you'd be least happy with tonight: the runbook attributes 503s to pool exhaustion and says check `WORKERS` first. Turning it up while the queue backs up means you'd be manufacturing the failure whose first diagnostic step points back at the thing you just changed. A backed-up queue plus fresh 503s is a much worse night than a backed-up queue.

Two things that follow from that:

- Config is read at boot, so a `WORKERS` change wouldn't take effect until a restart anyway. The deploy would supply one — which makes it easy to slip the change in alongside the roll without it looking like a separate action. It isn't safer for being bundled.
- If you genuinely need more concurrency, the ceiling moves by raising the vendor pool, not by editing config. That's a vendor conversation, not something tonight can solve.

**On the drain itself:** the runbook doesn't give you a throughput lever. `RETRY_BACKOFF=2s` is the one value explicitly marked never measured and free to change — but nothing says it affects drain rate, and if the backup is throughput-bound rather than retry-churn, lowering it just adds vendor load. `BATCH_SIZE=200` is listed with no annotation at all: no license, no prohibition, and no staging to try it in. I'd treat the queue as draining at whatever 4 workers give you, and let it.

Worth expecting: the roll will make the backup *worse* before better. Instances cycle with `SHUTDOWN_GRACE=30`, so you're running at reduced capacity for the duration, against a queue that's already behind.

## While you're on call

- Alerts may fire as **`ledger-forwarder`** — that's this service, not a second one.
- The synthetic check runs every minute against a fixed record id and alerts on its own if the vendor is down. During a pause or a quiet stretch, an alert with no traffic behind it may be the synthetic, not your roll.
- There's no staging by design — the vendor bills per tenant and finance declined a second one. Tonight's run is the first exercise of this migration anywhere.

The Friday-deploy caution doesn't apply — 2026-09-08 is a Tuesday, so reconciliation Saturday isn't the next thing downstream of you.
