**Short answer: conditional yes — but the switch itself isn't the risky part, the note's unchecked assumption is.** Don't flip it over blind. The note explicitly says "whether anything else also requires one-at-a-time has never been checked" — that's not a throwaway line, it's an open question that determines whether this is a safe latency win or a data-loss bug.

What to verify before switching, roughly in order of how likely each is to bite you:

1. **Partial-failure semantics of `write_batch()`.** The big one. Today, if record #47 of 100 fails, you know exactly which one, and the other 99 already succeeded independently. Find out whether v4.2's batch endpoint reports per-record success/failure or is all-or-nothing. If it's all-or-nothing, one malformed record now takes down 99 good ones that used to succeed on their own. Don't trust the docs here — send a batch with one deliberately bad record and see what actually comes back.

2. **What currently depends on one-call-per-record.** Grep every caller of `write_records()` and everything downstream for things keyed to "one call = one record": retry logic, per-record metrics/logging, rate limiters, circuit breakers, idempotency keys, callbacks fired per write. Any of these assumed 1:1 silently and need rework, not just the write path.

3. **Ordering guarantees.** Does anything downstream assume records land in submission order, or that a failure at record N means N+1...end were never attempted? Batch APIs sometimes don't preserve either guarantee on partial failure.

4. **Batch size / payload limits.** Check v4.2's docs for a max records-per-batch or payload size. If there's a cap, you need chunking logic, which reintroduces the partial-failure problem from #1 at the chunk level.

5. **Where records come from before hitting `write_records()`.** If callers already hand it a list and it currently loops internally, batching is close to a free win — N round trips collapse into 1, no latency downside. If callers instead invoke it once per single record synchronously, batching only helps if you *also* add a buffering/flush window — which trades per-record latency for throughput and is a much bigger change than just swapping the vendor call.

**Concrete plan:**
- Implement `write_batch()` behind a flag, alongside the existing loop — don't delete the fallback yet.
- Write a test that sends a batch with a bad record in the middle and asserts error handling still identifies which record failed, the way current callers expect.
- Canary on a low-stakes stream first; watch error rate as closely as latency — a latency win that silently degrades failure visibility is a regression, not an improvement.
- Only delete the one-at-a-time loop once the failure-mode test and canary both look clean.

Bottom line: batch it, but close the open question the note flags before you do, not after.
