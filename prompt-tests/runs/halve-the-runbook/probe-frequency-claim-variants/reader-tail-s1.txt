Working from the one crash line plus your runbook — I don't have the repo or the deploy history, so the diagnosis below is a shortlist, not a conclusion.

**Your runbook's entry for this doesn't cover it.** "Worker will not start" lists a missing env var (named in the first line) and an unrun migration (surfacing as a column error). Your first line names a Python symbol, not an env var and not a column — and an `ImportError` fires during import, generally before the process gets as far as reading config at all. This is the other tenth. Don't burn time on `WORKERS` or the rest of the environment.

**Stop the roll.** `deploy.sh` goes one pod at a time, so if it's still running, each remaining pod is about to be replaced with an image that can't boot. `kubectl rollout pause` — the runbook is explicit that paused is a normal state and nothing times out on it, so this costs you nothing. Then count how many pods are still on the old image; that tells you whether you're degraded or fully down.

**What the error means.** Something imports `RecordBatch` from `relay.vendor` and the deployed `relay.vendor` doesn't have it. Three shapes, roughly: the symbol was renamed or removed on one side of the boundary and the other side wasn't updated; the image was built from a tree where `relay/vendor` didn't get refreshed, so the two halves disagree; or something shadows the real module — a stale `.pyc`, or both a `relay/vendor.py` and a `relay/vendor/`.

Two things narrow it fast:

- **Get the full crash line, not just the first sentence.** The real message ends with the path of the file Python actually loaded, in parentheses — that one fact separates "wrong version of the module" from "wrong module entirely." And if the full line reads *partially initialized module … most likely due to a circular import*, it's a cycle, not a missing symbol: `RecordBatch` will be sitting right there in the file and grepping for it will send you the wrong way.
- **Run the image on your laptop.** No staging isn't a blocker here, because importing a module doesn't talk to the vendor — so this needs no second tenant and doesn't reopen the finance question. `docker run --rm --entrypoint python <image> -c "import relay.vendor as v; print(v.__file__); print([n for n in dir(v) if 'Batch' in n])"`. Then `git diff <last-good-sha>..<deployed-sha> -- relay/vendor` usually names the change outright.

**Recovering.** Rollback is the fast path, but check one thing first: did anyone run `./migrate.sh` this morning, and what did it do?

- Added a column → rollback is safe; old code just ignores it.
- **Dropped or renamed a column → rollback is not safe.** You'd be restoring code that references the old name — exactly the failure the runbook's ordering rule exists to prevent, 500s from every pod you roll back. That rule puts drops and renames *after* the roll finishes, and this roll didn't finish, so it shouldn't have run yet. Confirm it rather than assume; that's the ordering people get wrong under pressure.

**Around the edges, while it's down:**

- Records already in `pending` were handed to the vendor; over an hour there is a lost acknowledgement, not a lost record, so `./redrive.sh <id>` is safe — one at a time, never in a loop. If the outage leaves you a large pile of them, the runbook has no safe bulk answer: the single data point is ~900 in a loop rate-limiting the whole tenant for an hour, and nobody has worked out where the actual threshold sits. Get the worker up first and treat the backlog as its own decision.
- Reconciliation runs 04:00 Saturday and opens a ticket per discrepancy into **billing's** queue, which they triage Monday. If this drags to Friday, that's another team's Monday — worth a heads-up, and it's the situation behind the runbook's soft preference for having billing around on a Friday deploy. (That's a norm there, not a rule.)
- If alerts are firing, some may be the synthetic check, which hits a fixed record id every minute and alerts on vendor-side problems whether or not you're sending anything — check the vendor status page before pulling the vendor into this. Also note some alerts for this service still come through as `ledger-forwarder`.
- If you fix forward and that means rebasing anything already pushed, read `CONTRIBUTING.md` §4 first.
