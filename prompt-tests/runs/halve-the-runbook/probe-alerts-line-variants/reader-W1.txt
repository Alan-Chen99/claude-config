**Nothing that adds throughput — and the knob you'd reach for is already at its ceiling.**

`WORKERS=4` isn't a tuning parameter. The vendor pool is 5 per tenant and the admin console holds 1, so 4 is the entire remainder. Raising it to 5 or 6 doesn't buy capacity; it oversubscribes the pool and produces exactly the exhaustion the runbook names as the near-always cause of 503s. You'd be turning up the thing causing the symptom.

## Do first — both are checks or turn-downs

1. **Check the deployed `WORKERS` value.** The runbook says check it first on 503s, and the useful outcome of that check is finding it *above* 4. If someone already raised it chasing this same throughput problem, that's your incident. Set it back to 4.
2. **If it's 4, count open admin console sessions.** 4 + 1 = 5 = the whole pool, zero headroom. A second console session open is enough on its own to exhaust it. Cheapest possible fix, no deploy needed.

## The one config change actually available

`RETRY_BACKOFF=2s` is the only value the runbook marks free to change — never measured, so no baseline is being protected. Under sustained 503s your retries compete with new sends for the same 4 connections, so a 2s backoff spends scarce pool on re-sends. Raising it (5–10s, exponential if it isn't already) won't add throughput but stops you eating your own capacity.

Caveat both ways: never measured means there's no basis for the current value *or* the new one, and with no staging you're measuring in prod.

`BATCH_SIZE=200` is the only other candidate — more records per connection-hold rather than more connections. The runbook is silent on it, which is a genuine unknown rather than permission, and a bigger batch means a bigger blast radius when one fails. Deliberate experiment after the incident, not an incident action.

Config is read at boot, so any change means `./deploy.sh <env>` and a restart; `rollout pause` is safe. Today is Tuesday, so the Friday/billing caution doesn't bind — if this drags to Friday, pull billing in, since reconciliation is Saturday 04:00.

## Don't

- **Don't loop `./redrive.sh`** to drain the backlog. This is precisely what a backing-up queue tempts you into, and it's the one thing the runbook flatly forbids — ~900 records in February got the tenant rate-limited for an hour. The threshold is unknown, so there's no batch size you can call safe.
- **Don't flip `LOG_LEVEL=debug`** to diagnose this. It drops above ~2k lines/s, and under load you're above that — you'd lose exactly the lines you turned it on for.

## Before you size the backlog

Some of what's queued may not be undrained work. `pending` past an hour is a lost acknowledgement, not a lost record — the vendor likely has it already. Separate those out before sizing the problem, and don't redrive them blind or you'll double-send.

## The actual fix

The only real throughput increase is a pool larger than 5 per tenant, and that's a vendor conversation, not a config change. One thing to raise while you're in it: `STRICT_ORDERING=0` rests on an inference from acks that was never confirmed with them. If you do get more concurrency, you'd be scaling up an unverified ordering assumption at the same time.
