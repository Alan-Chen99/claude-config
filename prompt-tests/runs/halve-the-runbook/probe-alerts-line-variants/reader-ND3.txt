## Order of operations

Your change is a **drop**, so the migration goes last.

1. **Confirm the new build doesn't read or write `legacy_id`.** The drops-after rule only holds if old instances — which keep serving through the entire roll — still find the column, and new instances don't need it gone.
2. **`./deploy.sh <env>`.** Not `shipit`. Both work, but swapping the deploy tool is a conversation, not a change to make while on call.
3. **Wait for the roll to actually finish** — every instance on the new build. `SHUTDOWN_GRACE=30` means each instance takes up to 30s draining in-flight sends, so "first instance is up" isn't "the roll finished." The rule is written against roll completion, not the first restart.
4. **`./migrate.sh`** to drop `legacy_id`.

If anything looks wrong before step 4, `rollout pause`. Nothing times out on a paused roll, and a paused roll is a safe state: mixed versions, column still present. That's what the ordering buys you.

After step 4 you're past the reversible part. The code roll can be re-rolled; a dropped column can't be un-dropped, and with no staging this migration will never have run anywhere before it runs in prod. The runbook has no migration-rollback story — worth knowing yours before step 4, not after.

Two things to check that the runbook doesn't answer:

- **Does reconciliation touch `legacy_id`?** It runs Sat 04:00 (Sept 12) and tickets to billing. Eleven weeks of no false positives is a baseline you'd be perturbing.
- **`CONTRIBUTING.md` §4 governs force-pushing** if the branch needs cleanup. I don't have that file.

Timing is clear: today is Tuesday, so the Friday/billing caution doesn't apply, and it's not month-end.

## Worker count: leave it at 4

Raise it *to* 4 if the env is currently lower — that's the only "more workers" available to you.

`WORKERS=4` isn't a tuning default, it's arithmetic: the vendor pool is 5 per tenant and the admin console holds 1. That hold reads as standing, not "while someone's logged in," so 5 isn't yours even at 3am with nobody on the console.

Going past 4 doesn't drain the queue faster, it exhausts the pool — which surfaces as 503s, and the runbook's own 503 triage says check `WORKERS` first. You'd be manufacturing the exact failure mode you'd then be told to look for. Since config is read at boot, the change would have to ride this restart, so you'd turn a slow queue into a failing one at the same moment you're rolling new code with no staging behind you. Separately, more parallelism leans harder on `STRICT_ORDERING=0`, which rests on an assumption inferred from acks and never confirmed with the vendor.

The uncomfortable part: **nothing in the runbook adds send capacity.** `BATCH_SIZE` is the vendor's limit, `WORKERS` is bounded by the vendor's pool. The backlog drains at the rate the vendor accepts, and the deploy doesn't change that either way.

What's actually open:

- **`RETRY_BACKOFF=2s`** is the one knob explicitly never measured, and the runbook calls it a fine place to start if retries need work. It's only your lever if the backlog is retry churn rather than real volume — and nothing in the runbook tells you how to distinguish those. Split that first.
- **Don't loop `./redrive.sh`.** A backed-up queue is exactly the shape that makes bulk redrive tempting. One at a time by design; February was ~900 records and an hour of tenant rate-limiting, and the threshold is still unknown.
- **Don't flip `LOG_LEVEL` to debug** to watch it drain. Debug drops lines above ~2k lines/s, and a draining backlog is when you'd cross that — you'd lose the lines you turned it on for. It also needs another restart.

On alerts during the roll: the synthetic check hits a fixed record id every minute independently of your traffic, so quiet doesn't mean healthy and a firing alert may not be yours. Older alerts arrive as `ledger-forwarder` — same service.
