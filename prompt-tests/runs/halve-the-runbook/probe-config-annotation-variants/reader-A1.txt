Turning WORKERS up is the wrong move — do the opposite.

The runbook's own diagnosis gives this away: 503s under load = pool exhaustion. That means the vendor's capacity is *already* maxed out at your current concurrency. Adding more workers throws more concurrent requests at a pool that's already full — that raises the 503 rate, it doesn't fix it. Every 503 triggers a retry (`RETRY_BACKOFF=2s`), so more failures means more retries, which is exactly why your queue is backing up faster than it drains. That's a retry-storm feedback loop, and pouring more concurrency into it makes it worse.

**Concrete action: turn `WORKERS` down** (e.g. 4 → 2), not up. Less concurrent pressure on the vendor's pool → 503 rate drops → your effective throughput (successful sends/sec, not attempts/sec) goes up, because you stop burning requests on failures that just get retried anyway.

Two things to watch:
- `WORKERS` is read once at boot, so this needs a restart. Use `kubectl rollout pause` (the runbook explicitly calls this safe) to roll the change out gradually and confirm the 503 rate is actually falling before going all the way.
- The runbook flags these config values as guesses, not tuned numbers — worth checking the vendor's docs for their actual documented concurrency limit so you land on a real number instead of guessing a second time.

If you still want more throughput once 503s are under control, look at `BATCH_SIZE` (fewer, larger calls) instead of concurrency — that's a separate lever that doesn't add pool pressure the same way, though the same "it's a guess, check the docs" caveat applies there too.
