Don't touch `WORKERS` or `BATCH_SIZE` — both are already pinned at hard ceilings, not tuning knobs. `WORKERS=4` is the max the vendor's per-tenant pool allows (5, minus 1 reserved for the admin console) — you're already there. `BATCH_SIZE=200` is the vendor's documented max. Raising either just reproduces the exact `pool exhausted` 503 the troubleshooting section already warns about, except constantly instead of occasionally.

That means with today's setup, throughput is capped regardless of what you change in this relay's own config — the ceiling is external. Concretely, in priority order:

1. **Go talk to the vendor now, not next quarter.** You need either a bigger per-tenant pool, or a second tenant so you can shard across two independent 5-slot pools (two relay deployments, `WORKERS=4` each → 8 effective concurrent slots instead of 4). This is the only actual capacity lever available, it's on the vendor's timeline, and it's the one thing here you can't just flip yourself — start it today given a quarter's lead time.

2. **Re-measure `RETRY_BACKOFF` before you need it.** It's a guess that's never been load-tested. At 2x volume you'll be running much closer to the pool ceiling continuously, so transient 503s go from occasional to routine — an untested fixed 2s backoff across 4 workers risks synchronized retry storms that turn brief pool contention into sustained exhaustion. Test it under simulated load; move to backoff-with-jitter if workers are retrying in lockstep.

3. **Load-test `SHUTDOWN_GRACE=30` at the new volume.** If workers spend more time queued against the same 4-slot ceiling, in-flight sends at deploy time take longer to drain, and you'll blow through the 30s grace period more often. Not dangerous — stuck records just need `./redrive.sh`, one at a time, which is safe — but it'll go from rare to routine, so it's worth re-measuring and bumping if the drain time doesn't fit.

4. **Leave `LOG_LEVEL=info`, and don't flip to debug when you're troubleshooting the above under load.** Debug is one line per record; the pipeline drops above ~2,000 lines/s, so debug at 2x volume is more likely to lose exactly the lines you turned it on to see. Worth separately confirming info-level logging itself has headroom at 2x record volume — if it's already close to that ceiling, fix that before you need the visibility, not during an incident.

5. **If the fix in #1 involves sharding across two tenants, partition consistently (e.g., by account, not round-robin).** `STRICT_ORDERING=0` is currently safe because nothing depends on send order — but that holds because everything goes through one pool today. Splitting traffic across two independent pools means two independent send orders; keeping each entity's records on the same shard avoids introducing a real ordering problem where there wasn't one.

The one-sentence version: the config already tells you WORKERS/BATCH_SIZE can't move, so the actual scaling work is a vendor conversation about pool size, not a config change — everything else here is hardening for once you're running closer to the ceiling.
